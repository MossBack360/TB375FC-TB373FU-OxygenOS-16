# PiP corner weight: first confirmed geometric consumer (2026-10-27)

Scope: offline comparison plus a reversible, live A/B on OxygenOS 16. The live experiment is a temporary bind mount, not an installed module.

## Verified path

1. `SurfaceControl.Transaction.setCornerRadius` in the saved OxygenOS `framework.jar` routes to `nativeSetCornerRadiusExt(radius, defaultWeight)` when smooth radius is on. The plain native call uses the same radius but does not supply a weight.
2. OxygenOS `libgui.so`, `SurfaceComposerClient::Transaction::setCornerRadius` at `0xe9c70`, writes radius to `layer_state_t + 0x17c` and sets change bit `0x80000000`. Its Ext counterpart at `0x16a4a0` performs both operations and also writes the weight float to `layer_state_t + 0x0c`. Neither function calculates a curve.
3. The saved SurfaceFlinger dump observes the resulting active Chrome child layers with `weight=1.7` in stock mode or `weight=2` under the scoped native hook, so the extra state reaches the compositor. This observation does not identify the first SurfaceFlinger read of the field.
4. OxygenOS SurfaceFlinger exports `SkPath::addRRect(SkRRect const&, SkPathDirection, unsigned int)` at `0x440bc0`. At `0x440c54` it loads `SkRRect + 0x38` (weight); at `0x440c74` it selects this versus a fallback; at `0x440e8c` and subsequent corners it passes the selected weight in `s4` into `SkPath::conicTo`. This is a confirmed geometric use of the weight in the Skia code. The wrapper `SkPath::addSmoothRoundRect` at `0x7584c0` stores the supplied weight into `SkRRect + 0x38` before calling `addRRect`.
5. The corresponding ColorOS `SkPath::addRRect` is at `0x444ac0`. A bounded, address-normalized comparison of the 382 ARM64 instructions in both functions found zero mnemonic/operand differences. ColorOS likewise loads weight at `0x444b54`, selects it at `0x444b74`, and passes it to `conicTo` at `0x444d8c` and following corners. Thus this generic curve-construction code is not a demonstrated OOS-specific defect.
6. OxygenOS `SkPath::conicTo` at `0x4411c0` checks whether weight is positive and whether it equals 1, then passes non-unit positive weight to `SkPathRef::growForVerb` at `0x441250`. It does **not** have a special 1.3/1.7 threshold. This is curve construction and representation, not proof of the final per-pixel raster/clip evaluation.

## Remaining boundary

The static evidence does **not** yet prove that the affected PiP layer's display/capture render pass invokes this particular `SkPath::addRRect` entry; Skia has multiple rounded-clip representations. Nor does it prove the exact SurfaceFlinger layer-state consumer or which OPlus RenderEngine extension branch the affected layers take. The paths are a confirmed implementation of weight-based geometry, not an observed Chrome runtime call stack.

The saved `librenderengineextimpl.so` binaries do differ in `SkiaRenderEngineExtImpl::forceNoClipSmooth(SkRRect&, DisplaySettings const&, float, LayerSettings const&)`: OxygenOS entry `0x1a3a80`, ColorOS entry `0x1eec40`; even the initial gate differs (`b.ne` vs `b.eq` after corresponding comparisons), and a later radius adjustment uses 1.25 vs 1.2. This is a candidate compositor-side difference, **not a verified Chrome PiP hit or root cause**. It checks display/layer flags and names. Do not transplant the function or replace the entire binary until its relevant input path is established. A prior whole-SurfaceFlinger swap failed to start due an OOS `libgui` ABI mismatch (`IGraphicBufferProducer::setBbqQueuedBufCnt(int)`).

A further ABI difference is already visible at the producer boundary: ColorOS `libgui.so` exports `Transaction::setCornerRadiusExt(SurfaceControl const&, float, float, int)` at `0x172f30`; it stores the additional integer at `layer_state_t + 0x10` along with weight at `+0x0c`. OxygenOS exports only the three-argument variant at `0x16a4a0`, storing radius and weight but no integer. The ColorOS layer-state structure is larger (radius offset `+0x1cc` versus OOS `+0x17c`), so these offsets are build-local, not interchangeable. The integer's semantics and the value passed from the Java/JNI caller remain unknown. This makes direct method copying or binary grafting unsafe; it does not prove the extra integer fixes Chrome PiP.

## Live discriminator (2026-10-27)

With `debug.skia.force_noclip.logout=1` and SurfaceFlinger restarted, the affected Chrome video child `com.android.chrome/ChromeChildSurface#318` logged both `Skip Smooth ... zoom = 0, sv = 0` and `No Smooth ...` from `SkiaRenderEngineExtImpl::forceNoClipSmooth`. Its observed video buffer was 800 x 432, displayed at about 994 x 538, with its own rounded clip. The outer Chrome child remained a separate visible layer. Google Maps was re-entered into normal PiP under a live filtered logcat; no corresponding `SkiaReExtImpl` log was emitted. This is an observed branch-hit difference, **not proof that Maps never calls the function**.

OxygenOS's function at `0x1a3a80` remaps the incoming weight approximately as `r = ((weight - 0.99) / -1.01) * 0.33 + 1.33`. For an eligible layer and `r` in roughly `[0.99, 1.34]`, it rebuilds the `SkRRect` radii as `old_radius * r * 1.25`, sets the round-rect weight to 2.0, and logs `No Smooth`. At weight 1.7 this is about 1.37 times the original inner radius; at 0.5/0.6 the remapped value is out of range and this branch is skipped. That agrees with the prior weight experiments. The normal ColorOS function has stricter display/layer entry checks and uses a 1.2 radius multiplier. Static code alone does not establish which check ColorOS's Chrome layer takes.

For a short A/B, the saved OxygenOS `librenderengineextimpl.so` (SHA-256 `dc12fd204d76591d231ae3f62034779112c25b664593f2aa110ce2ac460acd35`) was copied and patched at file/virtual offset `0x1a3a80`: only `c8 23 00 b0` (`adrp x8`) became `c0 03 5f d6` (`ret`). The four-byte-only output has SHA-256 `7c5c7c37234886135482c69fc0bbc50b3b2b9ca8f38544d12ccc7df0336de895`. It was bind-mounted over `/system_ext/lib64/librenderengineextimpl.so` in the global mount namespace; the SurfaceFlinger mount namespace was checked to resolve that exact hash. The scoped PiP hook was changed from `native` to `stock`, so PiP still passed the original Ext weight. SurfaceFlinger started successfully. User test: the same Chrome video produced a **normal stable corner and no entry jump**. This is strong causal evidence that `forceNoClipSmooth`'s downstream transformation causes the observed Chrome mismatch; it does not yet show that disabling the function for every system layer is a safe permanent fix.

The test bind mount is **non-persistent** and disappears on reboot. `debug.skia.force_noclip.logout` was restored to `0` and SurfaceFlinger restarted before the A/B. At the end of this experiment the live PiP hook property is `stock`, while the temporary patched library remains mounted. Reboot restores the original library; the PiP hook mode should then be returned to `native` unless a narrower patch is ready. Do not package the global `ret` as a stable module without checking other OEM rounded surfaces.

## Next narrowing step

Identify the exact `DisplaySettings` and `LayerSettings` flags on the Chrome child at the `forceNoClipSmooth` entry and compare them with the normal ColorOS gate. Prefer a condition that skips this transformation only for the affected Chrome video layer or its exact feature state. The normal ColorOS function's stricter gate is a candidate, but copying it wholesale is unsafe because the binaries' layouts and OPlus structures differ. Keep the temporary A/B reversible.

## Same-PiP Home / Settings / Recents gate check

The temporary no-op bind was lazily unmounted, and the stock OOS library hash `dc12fd204d76591d231ae3f62034779112c25b664593f2aa110ce2ac460acd35` was verified before restarting SurfaceFlinger with `debug.skia.force_noclip.logout=1`. The scoped PiP mode stayed `stock`, so this run used the original Ext weight and original native function. The same Chrome child was `com.android.chrome/ChromeChildSurface#176` throughout; the PiP was not recreated for the foreground-state comparison.

- On OPlus Home, `SkiaReExtImpl` repeatedly logged `Skip Smooth: ...#176 zoom = 0, sv = 0` and `No Smooth: ...#176` on redraw.
- Opening Settings via `android.settings.SETTINGS` kept the PiP layer visible. The `#176` SurfaceFlinger frame counter advanced from 3521 to 3616 while Settings remained focused, yet the `No Smooth` log stopped after the transition. This rules out a paused video as the reason for the missing hit.
- Pressing Home resumed repeated `No Smooth` logs for the same child. Entering Recents through key event 187 left `recents_animation_input_consumer` present and the same Chrome child continued to log `No Smooth`.

The result supports a **Home/Recents-dependent render gate or render path**, not a direct Launcher call to this function. `forceNoClipSmooth` belongs to the SurfaceFlinger RenderEngine extension and receives `DisplaySettings` and `LayerSettings`; its branch checks display flags at offsets `0xd0`, `0xd5`, `0xd6` and layer state/name. The exact changing field has not yet been measured. A successful targeted patch must first identify that field, or constrain the modification to the affected Chrome child, rather than globally returning from the function.

After the check, the debug property was restored to `0`, the temporary four-byte no-op library was remounted, and SurfaceFlinger PID 9874 was verified running with patched library SHA-256 `7c5c7c37234886135482c69fc0bbc50b3b2b9ca8f38544d12ccc7df0336de895`. The live PiP hook remained `stock`. The bind is non-persistent and a reboot restores the original library.

## 2026-11-09 function-entry uprobe: exact gate byte

The tablet still had the same non-persistent four-byte no-op library mounted (SHA-256 `7c5c7c37234886135482c69fc0bbc50b3b2b9ca8f38544d12ccc7df0336de895`), so an arm64 uprobe at file offset `0x1a3a80` could read arguments at function entry without letting the function mutate the `SkRRect`. Kernel `CONFIG_UPROBES` and `CONFIG_UPROBE_EVENTS` were enabled. Two temporary tracefs events recorded the `LayerSettings` name and bytes from the `DisplaySettings*` argument (`x2`). The event definitions are in local `out/pip-uprobe-trigger-2026-11-09/`.

For the same Chrome PiP child layers `ChromeChildSurface#273` and `#261`:

| Foreground | `DisplaySettings + 0xd0` | `+0xd1/+0xd3/+0xd4/+0xd5/+0xd6` | Function entry |
| --- | ---: | --- | --- |
| OPlus Home | `1` | all `0` in sampled calls | observed |
| Settings | `0` | all `0` in sampled calls | observed |

This corrects the earlier shorthand: the function **is entered in both states**; the Home-dependent difference is whether it continues through the OOS radius-transform gate. In OOS disassembly at `0x1a3aa0..0x1a3aec`, `+0xd0=1` with `+0xd5=0`, `+0xd1=0`, and `+0xd4=0` reaches the transform path. With `+0xd0=0` and `+0xd5=0`, it returns early. This exactly reconciles the earlier stock-library `No Smooth` log on Home and its absence in Settings. The proprietary field's semantic C++ name and the code that assigns it are **not yet recovered**; do not call it `isHome` merely from correlation. AOSP's public `DisplaySettings` declaration does not identify this OPlus-added offset.

A separate `screencap -p /dev/null` on Home while no Chrome PiP was active left the uprobe profile count unchanged at 259. This supports a distinct screenshot render route but is **not** a same-PiP screenshot proof. The tracefs events were disabled and deleted, and `tracing_on` was restored to its initial `0`; the temporary no-op bind and scoped PiP `stock` mode were left unchanged.

## 2026-11-09 Maps versus Chrome: the earlier shape gate

The `+0xd0=1` byte is **not sufficient** to reach the smoothing code. A short entry uprobe also recorded the incoming `SkRRect` type (`x1+0x30`) and two radius fields (`x1+0x10/+0x14`) while the no-op library was mounted. On OPlus Home, Google Maps' normal PiP `SurfaceView#407` and `MapsActivity#402` entered this function with `d0=1`, weight 1.7, but `type=0` and both sampled radii zero. Chrome's PiP had two visible child layers: `ChromeChildSurface#547` entered with `type=0`, while `ChromeChildSurface#574` entered with `type=3` and radius fields approximately 21.67 and 21.63 (32-bit floats). Both Chrome children had `d0=1`, weight 1.7. Chrome's main window also had `type=0`.

OOS function entry first checks the shape type (`ldr w9,[x1,#0x30]` at `0x1a3a88`); with the default `debug.skia.force_noclip` gate active, `type=0` takes the early return at `0x1a3a9c`, **before** the `DisplaySettings +0xd0` test. This explains why Maps can share `d0=1` and weight 1.7 with Chrome without reaching the affected radius transformation. The previously observed stock `No Smooth` log on Chrome is consistent with its nonzero-type child; because today's no-op library returns at entry, the new uprobe alone records inputs and cannot prove which later branch is taken. Do not describe `d0` as a PiP-specific or sufficient trigger. The probe was disabled and removed; `tracing_on=0` and `uprobe_events` empty were verified.

The same entry probe was briefly repeated on a normal VLC PiP while its video played. VLC's video `SurfaceView(BLAST)#1293`, background `#1294`, and `VideoPlayerActivity#1286` all entered with `d0=1`, weight 1.7, `type=0`, and both sampled radii zero. Thus VLC matches the Maps early-return shape condition at this function entry, unlike Chrome's `type=3` child. The probe was again removed and `tracing_on=0` verified.

## 2026-11-10 type=3 sufficiency test

A minimal, independently signed Android PiP test APK was built in `out/pip-type3-harness-2026-11-10/` and installed as `dev.fixo.piptypeprobe`. It draws two independently buffered SurfaceViews. A child `SurfaceControl` named `FixoRoundedChild` was created under one SurfaceView, and the OPlus `Transaction.setCornerRadiusExt(child, 42f, 1.7f)` method was invoked successfully. SurfaceFlinger reported the child visible with a buffer and `cornerRadius=<40,40>`, weight 1.7. Nevertheless, the child used `DEVICE` composition; the `forceNoClipSmooth` entry probe recorded `d0=1,d6=1,type=0`, radius zero. Therefore, simply submitting a rounded SurfaceControl does **not** synthesize Chrome's `type=3` input at this function. A five-second `screenrecord` still showed the test child's sampled entry as `type=0`. This app is a layer-construction probe, **not a valid type=3 visual A/B**.

The decisive control used the **same existing Chrome PiP child** rather than another app. On OPlus Home, `ChromeChildSurface#1965` entered with `d0=1,d6=0,type=3`, radius fields `0x41d4cd25/0x41d459aa`, and weight 1.7; sibling `#1945` was `type=0`. Bringing Settings to the foreground kept `#1965`, its `type=3`, radii, weight, and `d6=0` unchanged, while `d0` changed to 0. Prior stock-library visual/log comparisons established this same Chrome PiP is abnormal on Home and normal with Settings foreground. Thus `type=3` is **not sufficient** by itself. The identified input conjunction for reaching the suspect Home path is at least a nonempty rounded shape and the Home-associated `d0=1` gate; the exact proprietary meaning of `d0` and other downstream branch requirements remain unproven. Today's live library remained the four-byte no-op, so this uprobe verifies input differences, not the stock function's output. The probe was removed, `tracing_on=0` verified, and Home restored after sampling.
