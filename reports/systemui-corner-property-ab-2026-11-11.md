# OPlus transition radius property versus Android display corners

On 2026-11-11 the owner requested installation of the archived `fixo_launcher_corner_radius` v1.1-test to determine whether its `ro.oplus.display.rc.size` value supplies the original SystemUI drag-corner fallback.

Before installation, the live property was `65,65,65,65`; `dumpsys window displays` reported all four `mRoundedCorners` radii as 0, and `cmd overlay lookup android android:dimen/rounded_corner_radius` returned `0.0dip`.

The archived ZIP `16-transition-corner-radius-config-v1.1-test.zip` (SHA-256 `6ae7ca47383cf77d354553d6a5269a2b2adebf4df9a1e8509dbc35bd936dad4d`) contains only `system.prop` with `ro.oplus.display.rc.size=26,26,26,26` plus metadata. It was installed through Magisk and the tablet rebooted. After boot, the property was `26,26,26,26`, but all four `mRoundedCorners` radii and the framework overlay lookup still reported 0. SystemUI PID 2665 stayed stable across two checks.

The stock `FullscreenTaskIndicatorManager$SpringDragManager` calls `OplusFlexibleWindowAnimationUtils.getDisplayCornerRadius(Display)`, which reads `Display.getRoundedCorner()` rather than this property. The v0.5 SystemUI patch uses `FullscreenTaskImageView.getCornerRadius()` instead. Direct decompilation of the original SystemUI on 2026-11-11 confirms that this method **also calls** `getDisplayCornerRadius(Display)` internally; it then returns `dpToPx(max((int)(displayRadiusPx / density) - 8, 12))`. It is an adjusted minimum-12dp fallback, not an independent corner source. At the current 400dpi density and 26px framework radius, the computed return is about 30px; if the framework radius is zero it is still about 30px. Thus this property module does not remove the need for the separate SystemUI drag-corner fallback. Whether it changes other transition visuals is left to the owner's visual check. The freeform corner gesture module was not installed in this boot snapshot.

## Decompiled source of the two values

The live `/system/framework/framework.jar` SHA-256 matches local `extract/framework.jar` (`60ea788ac729e8f39c40c287ab91f65ce8575b2f4e560172d1d8de2add1cef37`). Focused JADX output is preserved under `out/display-rounded-corner-trace-2026-11-11/`.

SystemUI drag path: `SpringDragManager` -> `OplusFlexibleWindowAnimationUtils.getDisplayCornerRadius(Display)` -> `Display.getRoundedCorner(0..3)` -> `DisplayInfo.roundedCorners`. Current `services.jar` `LocalDisplayAdapter.LocalDisplayDevice.getDisplayDeviceInfoLocked()` assigns this field using `RoundedCorners.fromResources(...)`. `RoundedCorners.loadRoundedCornerRadii()` reads per-display arrays `config_roundedCornerRadiusArray` / top / bottom, or falls back to framework dimensions `rounded_corner_radius` / top / bottom. On the current ROM, all corresponding overlay lookups and all four reported display-corner radii are zero. This path does not directly read `ro.oplus.display.rc.size`.

Separately, the original OPlus Launcher `RoundCornerLoader.readCornerRadiusFromProperty()` does directly read `ro.oplus.display.rc.size` (or the secondary property for a folded display), parses comma-separated integers, and selects the minimum value. Launcher `SmoothRoundedProperties` also declares this property. SystemUI's one-handed `OneHandedDeviceInfoUtils.getDeviceCornerRadius()` reads the same property, but the inspected `SpringDragManager` does not call that helper. The property therefore has real consumers; it is simply not the source of `Display.getRoundedCorner()` in this ROM.
